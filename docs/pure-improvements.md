# Pure improvements

A pure improvement here is a correctness, strictness, or completeness fix that does not give up latency, throughput, availability, or a Raft safety property. Batching, pipelining, leases, PreVote, and CheckQuorum stay as in Prytolyn.

## Considered and rejected (tradeoff)

- Do not send AppendEntries until the leader has fsynced. That would serialize disk and network and add commit latency. Paper 10.2.1 allows the parallel send. The quorum rule above is the safety fix.
- Do not count any peer until every peer has fsynced, including delaying the follower ack until a later barrier beyond the existing force-before-ack. The existing group commit already acks after fsync. An extra barrier would add latency.
- Report leadership-transfer success at `TimeoutNow` send time. That is fewer messages to wait for and a weaker completion signal.
- Drive leases from `DateTime.UtcNow`. Wall time can jump. The monotonic clock is the non-tradeoff.
- Raise `PreVoteLeaderLeaseFactor` or the election timeout to hide stalls. That spends availability.
- Shorten the read lease to `min(election timeout, 2 heartbeats)` so PreVote can stay gated at two heartbeats. That made the steady-state lease 80 ms on a host whose election timeout is 150 ms. The lease is the election timeout, measured from send time, and PreVote and RequestVote use that same window. See the vote-gate note below.
- Refuse client proposals while leadership transfer is still catching the target up. The thesis refuses new proposals only after `TimeoutNow`. Refusing earlier drops availability during catch-up and does not change the safety argument.
- Block the Raft thread until an asynchronous apply finishes before taking a snapshot or restoring one. That stalls heartbeats and elections for the duration of apply. The same ordering is done by deferring the snapshot until `FinishApply`, which adds nothing while apply is idle.
- Lengthen the socket fixture's election timeouts, or retry `Put` when leadership moves, to hide a stalled writer. A refused, reset, or timed-out connect retries the same frame inside 75 ms, which is inside the 120 ms election timeout. Raising the fixture spends availability to mask a transport stall. `ConnectFailuresAndReset_originalPutStillCommits` uses the same 120/350/600 ms timeouts as `ThreeNodeTcp_electsExactlyOneLeader_andPutReplicates`.

## Vote gate and lease

Thesis section 4.2.3: a server disregards RequestVote received within the minimum election timeout of hearing from a current leader, unless the request carries the leadership-transfer flag. This code uses that same window W for PreVote and for RequestVote. W is the node's own minimum election timeout. The read lease is W measured from AppendEntries send time, so the steady-state lease is the host election timeout (150 ms), not two heartbeats (80 ms). `TimeoutNow` clears the lease. `Start` sets the contact time only when the node already has a term or a log; a fresh empty node has not heard a leader, so the first election is unchanged.

Measured failover, uniform timeouts, one heartbeat of stagger (`Phase123ReviewTests.Item2_staggeredContact_failoverDoesNotOverlapTheLease`, `Phase2ReadElectionTests.Finding3_staleLeaderLease_expiresWhenPreVoteWindowOpens`): T = 150 ms, heartbeat = 40 ms, the second partition is 40 ms after the first. A new leader exists 150 ms after the second partition, and the old leader's lease is already false. The node that heard the later heartbeat wins at its own election timeout. On main, PreVote was gated at two heartbeats and RequestVote was not gated, so the earlier node could win about one heartbeat sooner. The added delay in this run is about one heartbeat, not an extra election timeout.

Measured failover when timeouts differ (`ElectionUnavailabilityTests.IsolateLeader_successorCommitsNewPut_windowWithinPaperBound`): the candidate's timeout is 200 ms and the voter it needs is configured at 400 ms. The successor commits at 400 ms. On main that voter granted the first RequestVote, and the window was about 200 to 220 ms. The extra wait is that voter's own election timeout. It is required for the lease: a voter that heard the leader inside its minimum election timeout must not grant a vote. Configuring every node with the same minimum avoids this gap.

A process restart that reloads a term or a log also waits W before it grants a vote (`DurableRestartTests.RestartAllThree_logsKeepCommitted_newTermProposeReappliesKv`). That is the same rule, applied because `Start` records contact at now. A cluster whose followers use a 400 ms timeout does not elect during the first 80 ms after that restart.
